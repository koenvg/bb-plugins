# Task outcome reports

Read this reference when review readiness, completion, failure, a blocker or a user decision needs a report in the linked work thread.

Write a short plain-language result with relevant checks, material limits and any decision needed. A single sentence is enough when it covers the outcome. Use any readable Markdown format; there is no word target or required bullet count.

For review or completion, name relevant passed, unrun or blocked checks. Do not present unrun checks as passed. Distinguish worker-reported results from checks you verified. A report does not change status or meet unfinished review or acceptance gates.

Keep logs, file lists, full commit hashes and detailed handoff evidence in the linked thread or an artifact. Preserve exact commits and baselines in handoffs. Use real task, thread, PR or attachment links.

If the user requests a parent summary, read current relevant task/child state. Treat failed reads or conflicting state as unknown. Count only done children as done; child counts or worker reports do not prove parent acceptance. State remaining integration or acceptance work. Reporting does not authorize dispatch, task restructuring or approval.

Use the existing linked work thread for useful outcomes and questions. Reporting alone does not authorize a notification, polling or wakeups. There is no task reporting command or replacement timeline.
