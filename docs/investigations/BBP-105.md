# BBP-105: Code Cleanup test dependency security review

## Decision

Update `bb-plugin-code-cleanup` from the locked Vitest 3.2.7 to Vitest 4.1.11. Set the direct requirement to `^4.1.11` and regenerate the package lock. The lock also selects `@vitest/mocker` 4.1.11. Do not use `npm audit fix --force`, add an override, or change the public SDK pin.

The existing workflows do not expose the vulnerable handler. An update is still appropriate because Vitest 3 is not maintained and will not receive this fix. This removes the vulnerable development dependency instead of relying on workflow restrictions alone.

Scope is this package's development tooling. Runtime source, test assertions, public SDK contracts, and the isolated preview are unchanged. No live plugin install or reload is part of this task.

## Advisory and exposure

The baseline `npm audit --json` reports two moderate package findings, for `vitest` and `@vitest/mocker`. Both refer to the same advisory, not two separate vulnerabilities:

- [GHSA-82fw-gwwq-j7x9](https://github.com/advisories/GHSA-82fw-gwwq-j7x9), CVE-2026-84373, path traversal and arbitrary file read through a redirect mock.
- Affected stable range: `>=2.1.0 <4.1.11`. Affected prerelease range: `>=5.0.0-beta.1 <5.0.0-rc.2`.
- Patched versions: 4.1.11 and 5.0.0-rc.2. The advisory states that older majors 2 and 3 will not receive a fix.

The public `mockerPlugin` and standalone `interceptorPlugin` register an unauthenticated Vite HMR WebSocket handler. A client that can reach that handler can register a redirect target outside the root, or a denied file inside it. The load hook reads the target without a file-serving allowlist check. An opaque URL scheme can preserve traversal segments. Ordinary normalized `file:` traversal examples do not reproduce that path.

Vitest browser mode has the same missing path check but registers mocks through token-authenticated RPC. It is not remotely reachable by default. This distinction matters: development-only dependencies and a loopback bind alone do not prove safety if the vulnerable handler is enabled or the server is exposed through a proxy.

The package's checked-in workflows do not register that handler:

- `npm test` runs `vitest run`. There is no Vitest configuration enabling browser mode or an exposed API. Tests use the Node environment or jsdom. jsdom is not Vitest browser mode.
- `preview/server.ts` uses plain Vite `createServer` with `configFile: false` and no mocker or interceptor plugins. It does not import Vitest. The fixture HTTP server binds to `127.0.0.1` and rejects unapproved Host headers before serving source or writing fixture state.
- The HTTP fixture test starts that plain Vite preview in a child process. The preview uses temporary fake-host SQLite, not production storage.

The exposure decision applies only to these checked-in workflows. It does not cover third-party servers, local configuration changes, added mocker plugins, or forwarded development servers. Keep the fixture local and do not expose it with secrets in its readable files. The fixture Host tests do not prove WebSocket security or test the upstream vulnerability directly.

## Version selection and compatibility

Registry metadata confirms that Vitest 4.1.11 supports Vite `^6.0.0 || ^7.0.0 || ^8.0.0`. The existing Vite 6.4.3 remains unchanged and is shared by the runner and mocker.

Vitest 4.1.11 requires Node `^20.0.0 || ^22.0.0 || >=24.0.0`. Its optional Node types peer accepts the existing `@types/node` 22 range. Validation used Node 24.15.0 and npm 11.12.1. Other Node versions were not tested.

The [Vitest 4 migration guide](https://vitest.dev/guide/migration.html) describes runner, mock, browser-provider, and coverage changes. This package has no custom pool, coverage provider, browser provider, or runner configuration. All existing assertions pass unchanged.

npm proposed Vitest 5.0.3 as its automatic major fix. Version 4.1.11 is the earliest patched stable major and supports the current Vite dependency. It avoids the larger Vitest 5 change and its higher Node requirement of `^22.12.0 || ^24.0.0 || >=26.0.0`.

`@get-bb/plugin-sdk` remains pinned to 0.5.9. The installed BB build tool warns that its own SDK is 0.5.29. The build succeeds with the existing pin; updating the SDK would be separate work.
